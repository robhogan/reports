Worker threads vs child processes in Metro

Whether Metro's transform workers should be worker threads (transformer.unstable_workerThreads) or child processes, measured on cold builds of Mattermost mobile on macOS, Linux and Windows, with per-job instrumentation to explain the differences.

Summary

On build time alone the choice barely matters: the two modes are within 5% of each other everywhere. Threads hand work to workers and back more cheaply. They start in about half the time, cost the main thread about half as much per job sent, and leave shorter gaps between jobs. They also use less memory, because the workers share one process. Against that, on a Mac running at full load each job costs more CPU in thread mode, which cancels the gains. That happens only once the machine is saturated, and nowhere else.

The stronger argument is what each mode makes possible. Only threads can share memory with the main thread, which is the route to a transformer that answers file-system and config questions from Metro's in-memory file map instead of doing its own I/O. Processes keep crash isolation and per-worker V8 flags. Either way, thread mode currently produces a different bundle from process mode, so that has to be fixed before it could become the default.

Where the difference comes from

With 8 workers on the Mac, threads win on every hand-off but lose on the cost of each job. Instrumenting every job, three builds per mode, shows both effects.

Per-job CPU is the worker's JS-thread CPU time for each file (process.threadCpuUsage), divided by the same file's time in a 2-worker process build. It excludes each worker's first 50 jobs, which include warm-up. Useful work per second is the reference CPU of all files transformed, divided by the transform phase's duration, so it discounts work done on slower cores.

The extra per-job cost appears only under saturation. At 2 workers, per-job CPU was ×1.00 for processes and ×1.02 for threads. At 4 workers it was ×1.13 and ×1.11, and threads finished sooner (18.6 s vs 20.2 s). The gap opens only at 8 workers, when the machine is saturated: system-wide idle CPU during an 8-worker build was under 5%.

The extra cost is in JavaScript itself, not in GC or messaging. CPU profiles of the 8 workers in each mode show Babel's own code running slower in thread mode, while GC and Node internals got cheaper.

Ruled out.

  • V8's helper threads. In thread mode all isolates share one V8 platform pool, 4 threads by default, where each child process gets its own. Raising the pool to 16 threads gave ×1.43 per job, and to 32 gave ×1.47, against ×1.48–1.59 by default.
  • A scheduling demotion. Sampled thread priorities were mostly 20 in both modes, decaying to between 10 and 20 under contention, as macOS does for busy time-sharing threads.
  • A shared V8 heap cage. The Node build used has pointer compression and its shared cage disabled.

Most likely cause (an inference). With the machine saturated, macOS places the threads of one process onto slower cores more often than it places eight separate processes. That fits two observations: the slowdown is uniform across JavaScript code, and it appears only at saturation. Confirming it needs per-cluster residency from powermetrics, which wasn't available.

Both machines also stop scaling early, for different reasons, and in both cases it's the same for threads and processes:

  • Linux: The 2 physical cores are the limit. Workers 3 and 4 share cores through hyper-threading, so each runs at about 60% speed, and total throughput rises only about 6% from 2 to 4 workers.
  • Windows: Per-job CPU nearly doubles at 8 workers. Effective clock speed dropped only 8–9% (from about 4.07 GHz at 2 workers to 3.76 GHz at 8), and kernel time stayed near 4% of job CPU. Four CPU-only busy loops beside 4 workers caused no slowdown at all. So the extra cost comes from Babel workers interfering with each other, most likely through the shared 16 MB L3 cache and dual-channel memory. That is an inference: hardware counters weren't read.

A correctness bug in thread mode

With transformer.unstable_workerThreads enabled, the release bundle differs from process mode. Reanimated's IS_JEST = !!process.env.JEST_WORKER_ID compiles to IS_JEST = true, which also switches its SHOULD_BE_USE_WEB on.

  • Threads see the variable. jest-worker sets JEST_WORKER_ID in each worker's environment. It does this for child processes too, but Metro passes its own forkOptions.env, which replaces jest-worker's environment object. So child processes only miss it by accident.
  • Plugins bake it in. react-native-dotenv inlines any process.env.* it reads from the build process, as do other env-inlining plugins.
  • Fix: Metro can delete JEST_WORKER_ID when a worker loads, in both modes. Doing exactly that made thread and process bundles byte-identical on all three machines.

What committing to one mode would enable

Threads.

  • Transfer instead of copy. Source and results could move between threads as transferable ArrayBuffers instead of structured-clone copies. A cold build of this app sends about 57 MB to workers and receives about 121 MB back.
  • Synchronous queries to the main thread. With a SharedArrayBuffer and Atomics.wait, a worker can block on an answer from the main thread. Workers could then look up files and Babel config locations in Metro's in-memory file map instead of searching the disk. That would make the transformer's inputs visible to Metro's invalidation.
  • Shared read-only data. Large byte data, such as a serialised file-map snapshot, could exist once rather than per worker.
  • Lower baseline costs. 6–19% less memory, about 100 ms faster start-up for the first job, and cheaper messaging on the main thread.

Processes.

  • Isolation. A native crash takes down only one worker, and workers can be recycled to contain memory leaks in plugins. In thread mode, an isolate running out of memory stops only its worker, but a native crash stops the server.
  • Per-worker V8 flags. Processes can be launched with flags of their own via execArgv, including ones NODE_OPTIONS rejects, such as --single-threaded-gc. Threads share one set of process-wide flags.
  • Better behaviour on a saturated Mac, as measured here.

Thread mode has two further requirements. Native addons loaded by Babel plugins must be safe in worker threads, and process.env is a per-thread copy, so code that relies on mutating it, as Babel transformers do with BABEL_ENV, behaves per worker.

Recommendations

  • Fix the JEST_WORKER_ID leak before recommending or defaulting to thread mode.
  • Treat threads as the direction. They're equal or better everywhere except a saturated Mac, they always use less memory, and they're required for shared-memory designs.
  • Avoid saturation on the Mac. Keep the default worker count at or below the number of performance cores: on this Mac, 6 workers matched 8 on build time with about 10% less CPU. That also avoids the only case where threads lose.
  • Re-measure the Mac case from a foreground terminal. These runs were launched with utility QoS (see Method), which may affect how macOS places threads.

Method

  • App and build. Mattermost mobile (React Native 0.83.9) at ad6b834, iOS release bundle (dev: false, minify: false, as React Native passes for Hermes), 7,082 modules. Built with Metro.runBuild using the app's own config, on Metro 5cfcfe21 with react/metro#2034 applied. The app's Babel path aliases moved from babel-plugin-module-resolver to its Metro config, and its block-list patterns were rewritten without a leading .*. Every build is cold: an empty transform cache with a warm file-map cache.
  • Machines.
    • Mac mini, M4 Pro (8 performance + 4 efficiency cores), 24 GB, macOS 27, Node 26.11.1. An iOS simulator and system daemons were running throughout, using about 2–2.5 cores. The benchmark processes ran at utility QoS (scheduling priority 20), and that couldn't be raised from the harness.
    • Intel i5-4278U, 2 cores / 4 threads, 8 GB, Linux Mint 22.3, Node 24.21.0. The bundle was byte-identical to the Mac's.
    • AMD Ryzen 7 7730U, 8 cores / 16 threads, 12.9 GB, Windows 11 Pro, Node 24.21.0, Defender real-time scanning on with no exclusions. The app was copied with workspace symlinks dereferenced, so its bundle differs from the other two machines', but not between modes.
  • A/B runs. Configurations run in interleaved rounds, 3 per configuration, reporting medians. CPU and peak RSS are sampled every 250 ms across the build's process tree (/proc on Linux, Win32_Process on Windows, ps on macOS). Thread mode is Metro's transformer.unstable_workerThreads; worker count is maxWorkers.
  • Instrumentation. Environment-gated timers in Metro's worker entry point and jest-worker's send and receive paths record, for each job:
    • wall time, JS-thread CPU time (process.threadCpuUsage, split into user and kernel) and process CPU time;
    • send and receive timestamps;
    • main-thread event-loop utilisation, sampled every 50 ms.
    Ratios compare each file with the same file in a 2-worker process build on the same machine. CPU profiles are from --cpu-prof, which in thread mode writes one profile per worker thread.
  • Supporting experiments.
    • V8 platform pool sizes via --v8-pool-size.
    • Scheduling priorities sampled with ps -M.
    • Effective clock speed on Windows from the % Processor Performance counter.
    • Contention tests running 4 workers beside 4, 8 or 12 CPU-only busy loops (a tight integer loop with no memory traffic).
