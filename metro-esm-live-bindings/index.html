Live ES module bindings in Metro, paid for by CallRequire

What a live-bindings design for Metro's ES module transform costs and saves in Hermes bytecode size, startup time and memory, once it is combined with Hermes's cached CallRequire, a runtime-defined __esModule marker and lazy re-exports, measured on a 5,000-module React Native release app.

Metro's ES module transform gives imports snapshot semantics: a binding copied once doesn't see later reassignments, and inside an import cycle it can capture undefined. Making bindings live costs bytes and helper calls. The design here recovers more than that cost from three changes that need the same groundwork: literal module IDs that let Hermes cache require results natively, a __esModule marker defined by the runtime from a per-module flag, and re-exports that evaluate their target on first read rather than up front.

The largest single effect on startup isn't liveness itself but laziness. Snapshot re-exports force every re-exported module to run when its barrel module runs. Live getters defer that, and in this app 35% fewer modules run before the first frame. Deferral departs from the spec's evaluation order, so it applies only under inline requires, which already defers imports the same way. With inlineRequires: false, re-exports stay eager and live, as the spec requires.

Tradeoffs

Inline requires only
Under inline requires, re-exported modules run later, or not at allA lazy re-export runs its target on first read instead of before the re-exporting module, which departs from the spec's evaluation order the same way inline requires already does for imports. That is the source of the startup win: about 2,100 modules ran before the first frame with eager re-exports and about 1,355 with lazy ones. Targets listed in nonInlinedRequires stay eager, and with inlineRequires: false every re-export keeps the spec's order.
3 → 30–57 ns per read
Reading a name through a lazy re-export is slowerA shared helper's getter costs 30–57 ns per read on an M-series Mac, against 3 ns for a plain data property and 20 ns for a getter emitted per name. Startup reads about 1,445 re-exported names, so the cost there is well under the time saved, but reads in hot render paths pay it every time. Resolving static reads past the re-exporting module at serialise time removes it.
All-or-nothing
Every serialiser that emits __d has to change with the transformOnce the transform stops emitting the __esModule marker, a serialiser that doesn't pass the new flag breaks CommonJS interop silently. That includes HMR updates, the lazy-definition serialiser and integrators' own serialisers. One opt-in option has to gate both halves, and be part of the transform cache key.
Edge case
CallRequire caches a module's first exports objectA module that replaces module.exports after an importer could already read it serves the stale object from then on. In Mattermost mobile, 1,039 of 7,170 modules reassign module.exports; 6 sit in a dependency cycle, and none can be read before the reassignment. Such modules need an uncached require path, decided at serialise time.
+8 B per module
The flags argument costs heap if stored naivelyKeeping the flag as a field on each module record adds 40 KB of JS allocation for 5,000 modules. Packing it into an existing field avoids that.
+0.37%
Classifying modules as ES modules costs build timeStatic detection of ES module interop adds 36 ms to 9.75 s of Babel transform time across the app's 4,987 modules, single-threaded.

The design

The design builds on earlier proposals by Rob Hogan, opened on GitHub and closed unmerged: tri-state ES module detection (react/metro#1862), live exports and imports (#1868, #1867, #1866, #1869), and a serialise-time rewrite of default imports described in #1865. Each decision sits where its facts are: per-module facts in the transform, graph facts in the serialiser, initialisation state in the runtime.

  • Transform, per module and cacheable. Imports become live as in #1869: a named import reads require(N).x at each use, a default import reads .default off a namespace-shaped helper result. Reassignments of exported bindings are mirrored into exports, as in #1868. Each module records its tri-state ES module status, whether an export can change after initialisation, and whether its exports object can be replaced. The __esModule marker statement is dropped. Re-exports follow inlineRequires: lazy with it on, eager with it off.
  • Serialiser, whole graph. Module IDs are inlined as literals and dependency arrays are dropped (Metro's serializer.unstable_inlineDependencyMap). Factories are wrapped in $SHBuiltin.moduleFactory with their real ID, so Hermes compiles require(<literal>) to CallRequire. Imports of known ES modules become plain require(N) reads, so they get CallRequire too. Each __d call carries a flags argument: ES module, don't memoise, has async paths.
  • Runtime. The module loader defines __esModule before running a flagged factory. The import helpers memoise only once a module has finished initialising, and never for flagged modules. Rarely used helpers, such as the lazy re-export helper, arrive on one extra factory parameter holding a shared object.

Metro main already emits the $SHBuiltin.moduleFactory wrapper behind customTransformOptions.unstable_staticHermesOptimizedRequire, but its open-source serialiser never substitutes the real module ID for the _$$_METRO_MODULE_ID placeholder. That substitution is the missing piece for CallRequire in open-source builds.

The full design is 3.06% smaller than the baseline. Dropping dependency arrays, CallRequire and the hoisted marker save 3.5% between them, live imports cost almost nothing, and lazy re-exports give back 0.4%. Per-name getters, as #1869 emits them, give back 2.1%.

  • The flag argument is free. Hermes compiles calls with up to four operands to Call1–Call4, which name each argument register (__d(f, id, deps) is a 6-byte Call4). A fourth argument switches to the 4-byte generic Call, and the constant loads it needs are mostly shared. Appending a 0 to every __d call alone saves 0.11–0.13%.
  • The marker is about 33 bytes per module. 4,573 factories each start with Object.defineProperty(exports, '__esModule', {value: true}). Defining it in the runtime saves 1.7% raw, but only 0.3% gzipped, because the statement compresses well.
  • The lazy re-export cost is getters. 3,402 re-exported names each become a getter. Built by one shared helper they cost 35 KB, emitted per name 187 KB.

Interaction with inline requires

Inline requires is what makes per-call cost matter: it turns every use of an imported name into a call. With it on, this app has 20,917 require sites, 5,701 default-import helper sites and 1,497 namespace-import helper sites, against 11,132, 4,158 and 412 with it off. By the first commit, about 9,200 require calls, 8,060 default-import calls and 1,175 namespace-import calls have run.

  • Named imports are already live at the import site. Inline requires turns x into require(N).x at each use, so a read always sees the source module's current exports.x. What's missing is the producer half: the source has to update exports.x when it reassigns x.
  • Default and namespace imports are snapshots today. Each use calls a helper that memoises its first result, even while the target module is still initialising inside a cycle. Rewriting the 92% of default-import sites and 86% of namespace-import sites whose target is an ES module to require(N).default and require(N) makes them live and lets Hermes cache them. The rest keep the helper, which memoises only once a module has finished initialising.
  • Re-exports are not inlined. A snapshot re-export, exports.x = require(N).x, runs when the re-exporting module runs, so it forces its target to run too, whatever inline requires does elsewhere. A lazy getter restores the deferral inline requires is meant to provide.
  • Memoising inline requires needs the namespace shape. With unstable_memoizeInlineRequires, a memoised helper result is pinned for the module's lifetime. Binding the namespace object and reading .default per use, as #1869 does, keeps memoisation and liveness compatible.
  • An existing bug splits an import in two. When inline requires inlines an expression a second time, through export default importedName or an alias such as const a = importedName, Metro's plugin loses the import's source location. The second use is then treated as a require, and package exports resolve it through the require condition. In this app that bundled both of i18next's builds, initialised one and passed the other to React, which suspended forever on a blank screen. It affects only the ES module transform with inline requires. The fix makes the plugin's location lookup prefer the location recorded by the first inlining, as collectDependencies already does. It isn't upstream at the time of writing, and every measurement here uses it.

Re-exports, the spec and inline requires

ECMA-262 evaluates every module a module requests, export … from targets included, before that module's own body, whether or not the re-exported names are ever read. It binds importers directly to the target's binding, so re-exports are both eager and live. Lazy re-exports keep the liveness but not the order, which is the same divergence inline requires already makes for imports, so the design ties them to that option.

  • inlineRequires: true. Re-exports are lazy getters built by the shared runtime helper. Targets in nonInlinedRequires, the existing list of modules that must run early, stay eager. Deferral belongs in the inline-requires plugin, which already owns the exclusion list and memoisation; the import transform owns liveness.
  • inlineRequires: false. Re-export targets are required up front, in source order. The serialiser keeps a plain snapshot, exports.x = _y.x, wherever it is equivalent to a live read, and otherwise emits an eager getter over the already-loaded exports object, get() { return _y.x }, with no require call per read.

An eager snapshot equals a live read unless one of three things holds, and in this app the first applies to 0.35% of re-exports:

  • The target shares a dependency cycle with the re-exporting module. It can still be initialising when the snapshot is taken, giving undefined, or a partial key set for export *. 12 of 3,415 named re-exports and 1 of 458 export * loops.
  • The target reassigns the export after initialising, directly or through a chain of re-exports.
  • The target replaces its exports object after it could have been read.

Reads that can see a partial value are rare in practice. Over a whole launch on the A16, a module whose factory was still running was read once with Metro's default transform and never with the ES module transform.

Recommendation

  • Substitute real module IDs in the $SHBuiltin.moduleFactory wrapper in the open-source serialiser, so unstable_inlineDependencyMap plus unstable_staticHermesOptimizedRequire yields CallRequire.
  • Fix the inline-requires location loss first: it breaks apps with dual-build packages under the ES module transform today.
  • Make the import helpers memoise only after initialisation completes. In release builds module.factory === undefined already marks that, so no new state is needed.
  • Ship live imports with the serialise-time rewrite to require(N) for ES module targets, and #1868's exports mirroring.
  • Add the __d flags argument with a bit for ES modules, and define __esModule in the runtime, gated by one option across transform and every serialiser.
  • Under inline requires, emit lazy re-exports through a shared runtime helper, keeping targets in nonInlinedRequires eager. Resolve static reads past re-exporting modules at serialise time to recover data-property read speed.
  • With inlineRequires: false, keep re-exports eager, as the spec requires: snapshots where they are equivalent to a live read, eager getters over the loaded exports object otherwise.

Method

  • App. A synthetic React Native 0.88.0-rc.4 release app with Hermes bytecode: React Navigation with 12 screens, Redux, React Query, Apollo, i18next and others, about 5,000 modules. Bundled with Metro 0.87.1, experimentalImportSupport and inline requires on, the default nonInlinedRequires list, and @react-native/babel-preset configured with disableImportExportTransform so ES modules reach Metro's transform. The plugin location fix described above is applied.
  • Variants. The design's transforms are applied by rewriting the bundle text with scripts, not by a modified Metro: inlining literal module IDs, dropping dependency arrays, wrapping factories, rewriting import helper calls, emitting re-exports as getters, and moving the marker into a flag with the matching runtime change. ES module status is read from each factory's marker. The exports mirroring of #1868 isn't modelled. Compiled with the app's hermesc (-O -output-source-map). Every variant renders the app on both phones. All device results are with inline requires on; the eager, live re-export form for inlineRequires: false wasn't measured.
  • Runs. One binary per platform embeds all four bundles, chosen per launch. 50 rounds per phone, each launching every variant once in shuffled order, warm page cache. Round 0 is dropped. Differences are medians of per-round differences with 4,000-sample bootstrap 95% CIs. Time runs to the first useLayoutEffect rather than the next frame, because on the A16 the gap to the next frame is bimodal (about 27 ms or 60–75 ms).
  • Counts. Separate instrumented builds log module initialisations, require and helper calls, and getter reads, in batches of 100–200 events with timestamps. Counts are to the nearest batch.
  • Microbenchmarks. Hermes CLI built at the app's Hermes version, with the bundle's real prelude and require polyfill, a target module, and a module that reads through each form in a loop. Best of 15 passes, three repeats.
  • Build time. The detection functions from #1862, run on each module's AST after @react-native/metro-babel-transformer, in one Node process, third warm pass of three.
