DartNative's launch benchmark, reproduced on an iPhone 12 mini

DartNative's chart, measured on an iPhone 16 Pro, puts DartNative first on both measures, ahead of React Native and Flutter. On an iPhone 12 mini, with the benchmark's own tools, DartNative ties React Native on both: to first frame, and to Home content on screen once DartNative's own correction for when each app writes its marker is applied. By the benchmark's uncorrected marker React Native is 20.5 ms ahead, because it writes the line about 15 ms before its content is committed. DartNative's lead over Flutter does reproduce, at 60–66 ms. The order held in both rotations, and each app's two rounds agree within 2 ms for first frame and 6 ms for Home content.

The benchmark's "first frame" is UIKit's first frame, and for all three apps that frame comes before any framework content. React Native's is an empty root view, DartNative's is its own launch placeholder, and Flutter's is its launch screen. Timed from iOS's own record of what each app sends to the screen, React Native commits its first real content 31.5 ms before DartNative, and DartNative 69.5 ms before Flutter.

Launch times on the iPhone 12 mini

Each app ran 10 measured launches in each of two rounds, in rotated order, using the benchmark's measure.py and Instruments' App Launch template. React Native and DartNative are within 4 ms of each other to first frame and to Home content on screen. React Native's home_ready line comes 20.5 ms sooner, but it writes the line before its content is committed. Flutter is 55–70 ms behind both on every measure.

What "first frame" and "Home content" contain

The benchmark takes first frame from Instruments' App Life Cycle, the end of UIKit's Initial Frame Rendering, and Home content from the moment each app writes SHOPBENCH home_ready. Neither marks the same thing in every app. The same recordings hold iOS's record of each Core Animation transaction an app commits, so the moment real content goes to the screen can be read directly.

  • React Native commits its first frame with an empty root view, then renders React's first content in a later commit. It writes home_ready from a React effect, before Home's content is mounted.
  • DartNative shows its own launch placeholder (DartNativeRuntime.showLaunch()) in sceneWillConnectTo and starts the Dart engine after that frame. It writes home_ready just after Home's content is committed.
  • Flutter's first frame is its launch screen; its content is drawn with Metal on the raster thread. It writes home_ready from a post-frame callback, before the raster thread presents the frame.

Against the published numbers

Absolute times differ by device and iOS version, so compare orderings rather than values. DartNative's iPhone 16 Pro numbers put it first on both measures. On the iPhone 12 mini, DartNative and React Native tie on first frame and on Home content committed; React Native is first by the uncorrected home_ready marker. The benchmark's own iPhone 12 results predate DartNative's app, but agree that React Native and Flutter are close to first frame there.

Is the code safe to run?

Nothing malicious was found in the code that was checked. The parts that couldn't be checked are DartNative's prebuilt engine and Dart SDK binaries and its compiled licence runtime.

  • Comparison apps. The Flutter and React Native apps in benchmarks/frameworks_comparison are byte-identical to whiskerrs/benchmarks' own at 635ec66, except that DartNative's copies omit the lockfiles (pubspec.lock, Podfile.lock). This run builds the benchmark's copies, lockfiles included. Build hooks are stock template script phases; npm packages resolve from the public registry, and none but fsevents has an install script.
  • DartNative's app. Its Dart source sends a GraphQL request to the configured endpoint, reads SHOP_API_URL with getenv over FFI, and doesn't cache or prefetch anything that could flatter its launch time.
  • The benchmark's tools. measure.py, bench.py, extract.py, the replay server and the XCUITest runner touch only the benchmark's own apps, Instruments and their output directory.
  • The dn SDK. It is a fork of Flutter's tool, shipped as Dart source and compiled locally; its closest upstream match is Flutter 3.41.0, with 533 of its 805 tool files identical. The 37 tool source files it changes without any DartNative marker add no network, process or credential access beyond one adb devices -l call. Its own network hosts are cdn.dartnative.com, dartpub.dev and api.dartpub.dev, and its analytics and crash reporting are switched off in source. The free trial sends api.dartpub.dev a SHA-256 of the Mac's hardware UUID with a fixed salt, a stable pseudonymous machine ID, and the returned token is compiled into builds.
  • Not audited. The Dart SDK and engine binaries downloaded from cdn.dartnative.com (the Dart SDK binary is ad hoc signed), and the licence and CodePush runtime, which ships as compiled kernel behind source stubs. DartNative's licence forbids reverse engineering.
  • Installer. install.sh replaces ~/zero if it exists and appends a PATH line to the shell profile. This run unpacked the SDK tarball into its own directory instead, after checking it against the published SHA-256.

Method

Reproduction steps

  1. Clone DartNative/dartnative at eca55b0 and whiskerrs/benchmarks at 635ec66.
  2. Install the DartNative SDK (1.7.0) from cdn.dartnative.com/dn_infra/sdk/latest/dn-sdk.tar.gz, Flutter 3.47.9, and CocoaPods; React Native 0.88.1 comes from the app's package-lock.json (prebuilt core, Hermes).
  3. Build each app's release build for the device with its BUILD.md: dn build ios --release for DartNative (its free trial covers this app's bundle ID), and xcodebuild for Flutter and React Native. Every app is built unsigned and signed afterwards with the same development identity and profile, keeping its bundle ID.
  4. Fetch the replay server's images with tools/replay/replay.py crawl, then run each app once against record mode so the replay set is complete.
  5. Build the XCUITest runner from tools/runner.
  6. Run tools/measure.py --rounds 2 --launch-runs 10 --journey-runs 0 --instruments "" for the three apps, with DartNative added to its APPS table as DartNative's README describes.
  7. Summarise with tools/extract.py --summary; the commit-time analysis reads the same traces.

Test conditions

  • Phone. iPhone 12 mini (A14), iOS 26.6.2, connected over USB, charging throughout: battery 86% at the start, 100% from the second round, at 22–28 °C. Battery health 77%.
  • Network. The phone reaches the replay server over Wi-Fi on the same LAN. The server ran on the Mac behind a small TCP forwarder in Node, because macOS Local Network Privacy blocked Python from the LAN; the forwarder adds about 1 ms per request. All runs had zero replay misses.
  • Mac and tools. Mac mini (M4 Pro), Xcode 27.0. Both published runs used Xcode 27.2.
  • Protocol. The benchmark's: each app is installed alone, its Local Network prompt answered by the runner, then it rests 180 s; one discarded launch, then 10 measured launches of 10 s each under the App Launch template with os_log, 5 s apart.

Changes to the benchmark's tools

  • measure.py: DartNative added to APPS, and the replay server's port made configurable so the forwarder can sit in front of it.
  • bench.py: the per-recording timeout raised from 130 s to 180 s, because Instruments takes 30–50 s to finalise each recording on this device.
  • The runner's prepare step waits for featured-collection instead of best-seller-0. On the iPhone 12 mini's 812-pt screen the best-seller grid starts below the fold, and DartNative only creates collection-view cells when they become visible. The step answers the Local Network prompt and isn't timed.

Things that change the result

  • Battery state. The same apps on the same phone, measured after its battery had drained, launched 32–56% slower, with the same order. Every result here was taken while charging.
  • Overlapping recordings. After each recording, Instruments requests a signature for every library the launched process loaded from the device, which keeps the phone busy for 30–50 s. A launch started during that window measured 7 ms slower to first frame (median of 8). Launches here never overlap; one launch cycle takes about 47 s.
  • The first commit isn't always the first frame. An app's first Core Animation commit came before UIKit's initial frame in 26 of 30 traces checked, so first frame comes only from the App Life Cycle table, which only the App Launch template records. Process start matches dyld's launch event (kdebug class 0x1f, subclass 0x7, code 0xd) to within 0.001 ms in the 9 traces checked.
