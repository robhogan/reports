Lazy module definition on two phones

What Metro's serializer.unstable_lazilyDefineModules does to startup time and memory in a 5,000-module React Native release app, measured in interleaved launches on an iPhone 12 mini and a Galaxy A16.

Lazy definition reliably cuts memory at startup: the ~2,000 modules that never run at startup no longer get closures, dependency arrays or registry entries. The define phase before the first module runs shrinks by 1.5–2.6 ms on the iPhone and 5.6–6.5 ms on the A16, but that work reappears on first require, so time to React's first commit doesn't improve.

The catch is the A16 when almost every module is required at startup. There, lazy definition costs 4 ms warm and 11 ms cold (3%) by the first commit, and the iPhone shows nothing comparable. Two things add up: defining about 3,000 modules one at a time costs more CPU than defining all 5,000 in one batch, and with a cold page cache the lazy bundle's definition code is read from flash in more, smaller reads.

Why the A16 pays when every screen loads at startup

The cost has two parts: CPU spent defining modules on demand, warm or cold, and extra IO from the lazy bundle's bytecode layout, cold only. A third bundle separates them. It keeps the lazy bytecode but calls the segment's definer for every module as soon as the segment registers, so all 4,993 modules are defined in one batch, as in the eager bundle.

99 paired rounds of eager, lazy and define-all, interleaved, with medians and 95% bootstrap CIs. This run alone is too small to resolve the 4 ms warm difference between lazy and eager, which the 576-round run above does.

  • Defining on demand costs CPU. In one batch, defining all 4,993 modules through the segment's switch takes 13.1 ms, the same as the eager bundle's __d calls (13.2 ms). The switch itself is cheap: the definer has 18 registers and dispatches through a jump table. Defining the 3,000 or so modules that startup needs, one at a time on first require, adds 11.7 ms (CI 7.7–14.6 ms) between first import and first commit compared with the batch. That's about 3.9 µs per module on demand against 1.4 µs in a batch, an estimate from these medians. Whether the difference lies in the runtime's require path or in lost locality wasn't separated.
  • The lazy layout costs about 7 ms of IO cold. Define-all pays 6.9 ms more than eager in its define phase cold, and nothing warm. That's the same total cold cost as lazy, which pays it later, during first requires. So this part comes from where the definition code sits in the bytecode, not from when modules are defined.
  • Same pages, more reads. A system trace of 20 paired cold launches shows the lazy bundle reading only 128 KB more of the bundle in total (+0.5%), but in 11 more reads before the first commit, with the JS thread waiting on IO 7.2 ms longer (CI 4.8–8.3 ms). Eager reads its 37 pages of definition code in two forward reads, the second grown by readahead to 32 pages. The lazy segment's definer is read in five reads of 1–16 pages, mostly moving backwards through the function, because Hermes lays out the switch cases in reverse order and modules are required roughly in ascending ID order. That accounts for about 3 of the extra reads. The rest fall in function bytecode and the bundle's header region, and weren't attributed further.

Method

  • App. A synthetic React Native 0.88.0-rc.4 release app with Hermes bytecode (hermesc -O), React Navigation with 12 screens, Redux, React Query, Apollo, i18next and others: 5,000 modules, 9.5 MB HBC. Every screen imported at startup runs about 3,000 modules. With screens on demand, screens other than the feed are required on navigation, through inline requires in getComponent.
  • Metro. Metro at 5cfcfe2 with a change that wires serializer.unstable_lazilyDefineModules into the server and the bundle command, installed over the app's Metro 0.87.1. Both bundles come from react-native bundle with the default serializer and differ only in the flag. Every module's source map positions are identical between the two.
  • Runs. One binary per platform embeds every bundle, chosen per launch. Each round launches every combination of layout, screens mode and cache state once, in shuffled order. "Cold" evicts the bundle's pages before launch: posix_fadvise(POSIX_FADV_DONTNEED) on Android, msync(MS_INVALIDATE) on iOS. The iPhone ran 50 rounds (400 launches). The A16 ran 24 runs of 25 rounds (4,800 launches).
  • Timing marks. Bundle start comes from a polyfill, first import from the first-imported module, and first commit from the feed screen's first useLayoutEffect. The requestAnimationFrame callback after the commit isn't used: on the A16, FlatList's second batch of cells sometimes renders before it and sometimes after, making the span bimodal (about 50 or 85 ms) in a way that shifts with small timing changes. A system trace and a CPU profile confirmed that both layouts do the same work there. The A16 build counts card renders to record this, in both layouts.
  • Statistics. Rounds pair the two layouts. Differences are medians of per-round differences with 4,000-sample bootstrap 95% CIs. Round 0 of each run is dropped as warm-up.
  • Android investigation. Perfetto system traces (scheduler, block IO, page-cache and CPU frequency events) around 84 interleaved launches with every screen imported at startup. Bundle reads are page-cache insertions for the APK within the bundle asset's range, mapped to functions with hbcdump function-info. The define-all bundle is the lazy bundle with a hook that calls the segment's definer for every module ID when the segment registers.
  • Correctness. A check mode requires all 11 deferred screens through the lazy segment after startup. It passed for every variant on both phones.
