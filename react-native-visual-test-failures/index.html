RNTester visual test failures, and what to do about them

Why the visual regression tests in React Native's CI failed in their first 13 days, from every report, capture log and differing screenshot, with each candidate fix evaluated against that data and on a simulator.

The pipeline itself worked: the deliberate change was caught, and no fix to comparison logic is needed. Nearly all differences came from screenshots taken at the wrong moment, and 41% of the PR reports with differences failed only because a bad screenshot had been published as the baseline on main. react/react-native#59408 (retake) now addresses most of that.

PR checks have been paused since 2026-10-29 by react/react-native#59629. Six small changes make them worth resuming as non-blocking checks: one fix to the iOS deep link, a content assertion, no comment when nothing was captured, the missing approval label, an upload retry, and continue-on-error on capture. With those, the replay predicts about 0.9% of PR reports with a false difference, from one known Android cause.

  • Bad baselines reach main unchecked. Of the 91 PR reports with differences, 37 (41%) had a correct capture and failed only because of a bad baseline. Another 9 had both, and 45 had only a bad capture.
  • Scroll. An end screenshot shows the start position, with a hash identical to the start test, or a mid-scroll position. waitForAnimationToEnd can return before the scroll runs or finishes.
  • Tap. view/z-index/reordered captured the unflipped order, and touchable/feedback-events/pressed lacked its pressIn line. #59413 fixed the switch case, which hasn't recurred.
  • Android inset. The same 12 tests changed in 4 runs. Tapped elements sit exactly 73 px higher in Maestro's log, for example [13,852] against [13,925], and the recorded environment is identical. A status bar or display cutout difference at boot is plausible, but it's unproven, because a crop never includes the top of the screen.

A real change that went unreported

text/text-align/default on Android changed permanently (f6824073 to ae8cd0b5) with no report showing it. It changed during the 2026-10-26 outage, when main published no baselines. The most likely cause is react/react-native#59504, which changed left-to-right text width on Android 15 and landed in that gap. That's inferred from the timing and the change itself.

The hidden failure behind the stale screenshot

On iOS, border.yml runs first and has failed its first attempt in every capture job since 2026-10-26. The capture script retries it, so the job passes and the failure doesn't show. button.yml runs next in that same first attempt, on an app that relaunched onto the Border example. It waits only for the generic example-container testID, which that example also has, so it photographs the wrong screen.

The change came from two deep-link fixes on 2026-10-26. react/react-native#59488 by Nicola Corti (@cortinico) removed a home screen wait that failed when RNTester restored another screen. react/react-native#59518 by Christoph Purrer (@christophpurrer) then sent each link twice, because a slow emulator dropped the first one before its JS listener was registered. Both solved a real problem. On a fresh iOS simulator, the second link appears to leave a second "Open in RNTester?" dialog over the example.

Do both the one-link fix and the assertion. The fix removes the cause, along with about one retry per job. The assertion stops the same class of stale screen returning, and it's a small change in the one flow that waits only on the generic testID. iOS capture's median job time went from 20.4 to 24.6 minutes across these changes, though not all of that is the retry.

Capture job failures

79% of the 139 failures were one outage of about 5 hours. #59488 removed the wait, then deep links arrived before RNTester's listener was ready, so most flows failed all 3 attempts until #59518 landed. On 2026-10-26, 58 of 148 Android and 47 of 86 iOS jobs failed, and 24 pushes to main published no baseline. #59488's own PR run showed Android failing 12 of 12 flows, so running capture on PRs that touch this code is a cheap guard. PR capture is currently paused, so these changes don't get that check today.

Upload and "no capture" noise

  • Uploads fail, and the rate is rising. 16 of the 17 compare failures were network or auth errors during upload or login, and 1 was a cancellation. On main, 2 of 141 pushes failed before 2026-10-30, and 11 of 77 since. A failure costs that commit its baseline, since the manifest is uploaded last, and later runs fall back to an ancestor. The cause of the rise isn't established. None was rerun, and the upload step has no retry.
  • "No capture" comments on PRs. The report step comments whenever a platform has an error. So 151 of 341 PR reports commented or updated a comment with no differences to show, and 70 of 195 PRs only ever had those. Most are path-filtered PRs, where a missing capture is expected.
  • Missing approval label. visual-change-approved doesn't exist on the repository, so the documented way to approve a change has never run.
  • Upstream failures block capture. build_android failed 164 times. 92 were one gradle-plugin compile error around 2026-10-27, and 70 were unit test or lint failures. Prebuild failures blocked 79 iOS runs. These PRs already fail for their own reasons, so capture adds little there.

What retake prevents

Retake re-runs a flow once if its screenshot differs from the baseline, and replaces it only if the retake matches. A transient capture on main then never becomes a baseline, so PRs have nothing bad to inherit. Replaying all 153 reports against those rules gives the table below.

In real runs since it landed, retake has cleared all 8 transient differences: 5 button/default-styling, 2 touchable/highlight and 1 view/z-index. One correct capture against a stale baseline differed twice and was kept, which repaired that baseline. 42 of the 87 PR reports clear on their own capture, and the other 45 need clean baselines. Scroll, notification and black screen cases haven't occurred since it landed, so those are projected.

The tradeoff is that retake also hides an intermittent rendering bug that renders correctly the second time.

Recommendation

  • Land the six changes above, starting with the one-link fix and the button assertion, and confirm on main that border passes first time.
  • Resume PR checks as non-blocking once main has run clean for a few days with retake. The replay predicts 3 of 341 PR reports (0.9%) with a false difference, and capture failures at about 2%.
  • Instrument the Android inset next. It's the only remaining source of false differences that retake can't reach.
  • Then work through the assertions, so retake is a safety net and not the main defence.

Method

Sources: all 527 results.json reports in the public baseline bucket (186 main, 341 PR), all 1,447 Visual Compare runs, jobs from 1,383 Test All runs, and logs for all 139 failed capture jobs. A difference's cause comes from viewing expected, captured and diff images for each distinct baseline and capture hash pair. The Android inset cases were classified by hash and by tapped-element bounds in Maestro's logs.

The retake replay assumes a transient capture repeats on retake at that test's own bad-capture rate, which predicts about 2 repeats among the 80 non-stale transient captures, and that retakes fail independently. The 0.9% figure counts Android inset reports only, and the deliberate PR isn't a false difference. Black screen causes are unknown, so counting them as cleared is an assumption.

The attempt-1 figures cover successful iOS capture jobs with logs. Local tests used CI's RNTesterApp-NewArch-Release build from main and simctl erase before each round.
