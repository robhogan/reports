Where Metro's transformer spends a cold build

Where the time goes when Metro transforms a large React Native app from an empty cache, and how well that work parallelises, measured by instrumenting every stage from the main thread through worker IPC to individual Babel plugins in a cold build of Mattermost mobile.

A cold build is bound by worker CPU, but parallelism stops paying off at 6 workers on this 12-core machine. Graph discovery is never the limit: within 1.5 s of the first transform there are hundreds of jobs queued. Past 6 workers, each job just gets slower (median 5.0 ms at 4 workers, 6.9 ms at 8, 9.8 ms at 12) and the hand-off between jobs gets longer. In worker CPU, Babel plugin visitors take about a third, Metro's own passes about 31%, and loading the Babel config 15%, because the config is loaded once for parsing and again for transforming.

Three changes cut cold-build CPU by 8–15% without changing a byte of output. They are: stop deep-cloning each AST in Metro's main Babel pass (react/metro#2034), load the Babel config once per file, and read files for the lazy SHA-1 off the main thread. The measurements also turned up a correctness bug: with transformer.unstable_workerThreads, Babel plugins can inline JEST_WORKER_ID into a release bundle.

Where the wall time goes

A cold release build takes 18.7 s, and 15.4 s of that is the transform window. The remaining 3.3 s is serial: the file map before the first transform, worker start-up, and writing the bundle at the end.

How well it parallelises

Speedup peaks at 3.6× with 6 workers. Metro's default formula picks 8 workers on this machine because os.availableParallelism() counts all 12 cores, including the 4 efficiency cores. Beyond 6 workers, wall time stays flat or gets worse, while total CPU keeps climbing.

The same 7,085 jobs cost 1.5× more CPU at 8 workers than at 4, and 2.4× more at 12. Each job also waits longer to start. At 8 workers, the main thread and the workers already outnumber the 8 performance cores, before counting V8's GC and compiler threads. Workers that land on efficiency cores or contend for memory bandwidth run slower, and a worker that has finished a job waits longer to be scheduled for the next. This explanation is an inference: it fits the core counts and the fact that both costs rise together, but per-core scheduling wasn't traced.

The dependency graph never starves the workers. More than 100 jobs are queued by 3.5 s into the build, and 800–1,270 from 5.5 s to 14.75 s. The median job waits 1.8 s in jest-worker's queue before it is sent. Only about 0.5 s of the transform window has fewer jobs in flight than workers, at the start and the very end.

Where worker CPU goes

Two-thirds of worker time is spent inside React Native's Babel transformer running the app's own config: loading that config twice (15%), parsing (8%), and the plugins (about 39% including Babel's traversal overhead). Metro's own work after that is about 31%, and the largest single piece is a deep clone of every AST.

Config loading is a flat per-file cost. It runs at about 1.0 ms in parseSync and 0.6 ms in transformFromAstSync for every file, steady from the start of the build to the end, so it isn't a cache that degrades. CPU profiles split it three ways. Over half is Babel's config-chain walk: overrides and include matching, and the package.json lookups that decide where .babelrc files apply. About a quarter is plugin descriptors, whose cache checks stat files on every load; react-native-dotenv's .env check alone is 0.9 s. Most of the rest is presets.

The main thread

The main thread is busy for 52% of the transform window, so it isn't the bottleneck. About 4.5 s of its 11.3 s of CPU is transformer work. The largest piece is reading every file synchronously to compute its SHA-1.

Warm builds

With every transform a cache hit, the build takes 3.7 s and the transformer is a small part of it. The file map takes 2.1 s, 1.85 s of which is the block-list expression. The 1.15 s transform window keeps the main thread 100% busy. Within it, cache reads (an async read, then JSON.parse on the main thread) take 0.24 s, SHA-1s 0.22 s and resolution 0.6 s. Serialisation takes the final 0.44 s.

What three small changes buy

Dropping the AST clone and loading the config once save 4–5% CPU each. The async read saves little CPU, but it shortens wall time by unblocking the main thread. None of the three changes a byte of the bundle. Together they cut CPU by 8% at 8 workers and 15% at 6 workers. Wall-time gains don't add up linearly, because at 8 workers the build is limited by cores, and CPU saved in one place partly turns into less contention elsewhere.

Run-to-run spread is about ±5% of wall time, so wall deltas under 5% are noise; CPU is steadier. Every variant produced a bundle byte-identical to its baseline.

The AST clone was a workaround for react/metro#641. @vzaidman traced the underlying bug in react/metro#2034. Babel reuses scope information cached by an earlier pass, so constant folding can delete a function that a later-inserted call still uses. The PR clears the scope cache right before constant folding instead of cloning. Mattermost uses the configuration from #641 (ES modules without experimentalImportSupport). Its bundles come out byte-identical with the PR's change in both release and dev, which adds an open-source app to the PR's own measurements (about 4% wall and 5% CPU averaged across three large production apps). Clearing the whole cache before the inline pass instead throws away scopes the Babel transformer has just built. That costs more in dev, where constant folding never runs.

A correctness bug in worker-thread mode

With transformer.unstable_workerThreads: true, the release bundle is different. Reanimated's IS_JEST = !!process.env.JEST_WORKER_ID compiles to IS_JEST = true, which in turn sets its SHOULD_BE_USE_WEB to true.

  • Worker threads see the variable. jest-worker sets JEST_WORKER_ID in each worker's environment. It does this for child processes too, but Metro passes its own forkOptions.env, which replaces jest-worker's environment object. So child processes only miss the variable by accident, and threads don't miss it at all.
  • Some plugins inline the build environment. react-native-dotenv, like any plugin that inlines process.env.* from the build process, bakes the value into the bundle.
  • Fix: Metro can remove JEST_WORKER_ID from the transform environment in both modes, so the worker type can't change output.

Outside the transformer: a 200× slower block list

Mattermost's resolver.blockList entries are written as /.*\.test\.(js|jsx|ts|tsx)$/ and similar, a common style in React Native apps. Metro combines them with its own [/\\]\.(git|hg)[/\\] into one unanchored alternation, and the leading .* makes it backtrack across every crawled path. Matching the project's 112,678 paths takes 1,582 ms as written, and 8 ms with each leading .* removed, with the same 1,230 matches. That is 16% of main-thread CPU in a cold build and about 45% of a warm one. Removing a leading .* from an unanchored pattern doesn't change what test() matches, so Metro could do it when combining patterns, or warn about it.

Recommendations

  • Land react/metro#2034. It saves 5–9% CPU and 7–9% wall on Mattermost, with identical output.
  • Load the Babel config once per file in @react-native/metro-babel-transformer. Call transformSync when the Hermes parser isn't in use, or call loadPartialConfig once and reuse the result. That saves 4–6% CPU. Expo's transformer wasn't checked.
  • Move lazy SHA-1 reads off the main thread. Either read asynchronously, or let the worker hash the file and return the hash with its result, and stop sending the worker source it can read itself.
  • Test a performance-core-aware maxWorkers default on machines with efficiency cores. Here, 6 workers matched 8 with 10% less CPU. Confirm on a quiet machine and on Linux before changing it.
  • Merge Metro's post-transform passes. Inline-requires and inline, constant folding, collectDependencies and the function-map traversal each walk the AST, and two of them also set up a fresh File and crawl scope. Together they are about 27% of worker CPU in release builds.
  • Start workers while the file map builds to save about 0.5 s on every cold start, and send the transformer config once per worker rather than with every job.
  • Fix the worker-thread environment leak before promoting unstable_workerThreads.
  • Normalise leading .* in block-list patterns.

Method

  • App. Mattermost mobile at ad6b834, which uses React Native 0.83.9 and babel-preset-expo 55.0.21. Its babel.config.js also adds @babel/preset-env, @babel/preset-typescript, transform-runtime, legacy decorators, module-resolver (27 aliases), react-native-dotenv, react-native-worklets/plugin and formatjs. Its Metro config is @react-native/metro-config with a custom resolveRequest, built here with Metro 0.87.1.
  • Builds. Metro.runBuild with the app's own config for the iOS entry point. Release builds use dev: false, minify: false, which is what React Native's Xcode script passes when Hermes is enabled, and produce 7,082 modules and 52 MB. Dev builds produce 7,316 modules. "Cold" means an empty transform cache with a warm file-map cache and Watchman off (Node crawler). The transform cache is outside the project root.
  • Machine. Apple M4 Pro with 8 performance and 4 efficiency cores and 24 GB, running Node 26.11.1 on macOS. The machine was not idle: an iOS simulator used about one core throughout, and system daemons occasionally added more.
  • Instrumentation. Timers inserted into Transformer.transformFile, jest-worker's send and receive paths, the worker entry point, every stage of metro-transform-worker, React Native's Babel transformer, and @babel/core's config loading, file set-up and per-pass pre, traversal and post. Per-plugin time comes from wrapPluginVisitorMethod, with nested calls subtracted. The main thread's event-loop utilisation was sampled every 50 ms. IPC sizes are v8.serialize lengths of the request and response messages, measured in a separate run. Instrumentation added about 4% to worker time with plugin wrapping and less without, and every toggle is off by default.
  • Profiles. --cpu-prof for the main process and every worker, in separate runs, for GC share, config-loading breakdown and main-thread activity.
  • A/B runs. Each variant is an environment-gated patch, run in interleaved rounds with medians reported. Every variant's bundle was checked for byte identity by SHA-1.
