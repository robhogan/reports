Terminal output and Metro's main thread

How much main-thread time terminal output takes during cold and warm Metro builds, when a terminal can hold a build back, and what react/metro#2162 changes, measured on real dev-server builds of Mattermost through real PTYs and terminal emulators.

The progress bar isn't a meaningful cost, even in a warm build, where the main thread is the bottleneck and each millisecond of writes adds a millisecond of build time. Its writes are driven by a timer rather than by module count, so they stay at about 0.5 ms per second of build however busy the main thread is.

Two things do cost main-thread time: log lines, which scale with how much is logged, and terminals that stop reading, because TTY writes block the main thread on POSIX. Every terminal measured reads at least 1,500× faster than the progress bar needs, so stalls and very slow links are the realistic risk, not terminal speed. react/metro#2162 makes log lines slightly more expensive and leaves the progress bar unchanged.

The progress bar's cost in a normal build

Terminal writes take 0.04% of main-thread time in a warm build and 0.13% in a cold one. Including everything else the reporter does, such as handling 14,638 progress events and formatting status lines, the totals are 0.25% and 0.37%.

A warm build doesn't make the progress bar relatively more expensive. The reporter throttles progress to one update per 100 ms, and each redraw is three short writes (move cursor, clear, status line), so the cost follows wall time rather than work done. In both build types that's about 0.4–0.7 ms of writes per second. What the warm build changes is how directly those writes reach build time, because a main thread that is 97% busy has no slack to absorb them.

Removing terminal output doesn't measurably change build time. Real emulators agree: warm builds spend 0.4–0.5 ms in writes in the app terminal, kitty and Terminal.app, and cold builds 5–11 ms.

Log lines are what cost main-thread time

Each line logged from the main thread during a warm build adds 13–34 µs. Without a worker in the path, that time comes straight out of the build: 7,317 lines add 94–248 ms, or 8–20%. Most of it isn't the write. With the fast PTY reader on the PR, 7,317 lines spend 30 ms in writes and 129 ms in the reporter, which formats each line and recomputes the status line.

Cold builds absorb logging better because workers set the pace and the main thread has slack. Worker output of 36,261 lines (3.8 MB) takes 0.2–2.3 s of main-thread write time, but the PR raises build time by only 0.6–2.1%. Those figures are in the PR section.

When a terminal can block a build

A terminal holds a build back only when it reads slower than Metro writes, or stops reading. Node puts TTY streams in blocking mode on POSIX, so stream.write on the main thread waits until the kernel accepts the bytes. A macOS PTY accepts 1,024 bytes with nobody reading, compared with 64 KiB for a pipe. That's about half a second of colour progress output.

A cold build loses almost as much as a warm one, despite having workers, because almost all of the pause lands on the main thread. Since one write spans the pause, the event loop can't run during it. That last point is inferred from the write being synchronous: the server's responsiveness during a stall wasn't probed separately.

^S depends on flow control being on. @react-native/community-cli-plugin puts stdin in raw mode for its key handler, which should turn flow control off, but that wasn't tested.

Impact of react/metro#2162

react/metro#2162 by @vzaidman makes Terminal.log() write immediately instead of queuing lines for the next status update, so logs stay in order with other output. The status path is effectively unchanged, so builds that log nothing are unaffected. Log lines are no longer joined, which raises writes up to 66× in a warm build and 18× in a cold one.

Recommendation

  • Performance isn't a reason to hold back react/metro#2162. Builds that log nothing are unaffected. The largest cost on a normal terminal is +7% on a warm build logging one line per module, and the larger +19% needs a 10 KB/s terminal.
  • Leave the progress bar's throttling alone. With at most 0.13% of main-thread time in writes, there's nothing meaningful to win back.
  • Reduce repeated main-thread logging where a warm build has it. Removing 7,317 lines saves 94–248 ms, more than any change to Terminal can, and most of that cost is in the reporter rather than the write.
  • Don't move terminal output off the main thread for now. It's the only complete fix for stalls, but these measurements don't show enough cost in normal use to justify it. This is a judgement call, to revisit if stalls turn out to be common.

Method

Each run starts a real Metro.runServer with TerminalReporter and requests one iOS dev bundle (7,316 modules, 59 MB) from a separate curl process. Build time runs from the request to curl exiting. The app is Mattermost mobile at ad6b834 on Metro 0.87.1, with its own Metro config, using the node crawler and a warm file map. Only metro-core's Terminal.js changes between sides, loaded at runtime from cddcf36 (main) or PR commit 8f027e2. The PR's later commit 47808a7 adds an await to waitForUpdates(), which isn't on the write path, and it wasn't measured.

Cold means an empty transform cache and warm means every transform is a cache hit. Writes are timed by wrapping process.stdout.write, which captures blocking because the writes are synchronous. Main-thread busy time is performance.eventLoopUtilization(), which counts time blocked in a write as busy.

PTY runs use a real PTY with a scripted reader that drains as fast as possible, at a set rate, or not at all. Emulator runs execute inside the app terminal panel of Claude Code's desktop app, kitty and Terminal.app. Comparisons between main and the PR use balanced ABBA order and a bootstrap 95% CI over per-group differences. The machine was shared with other work. Rounds waited up to 90 s for the 1-minute load average to fall below 5, but the balanced cold runs had a median load of 9.8. Differences under about 1% should be treated as noise unless a CI excludes zero.

Colour affects the byte counts. The reader-speed, warm logging and emulator runs have colour on. The balanced cold runs and the cold logging runs on the fast PTY have it off, at 9.4 KB of progress output against 20 KB, with similar write time (6.1 ms with colour, 2 runs).

What this doesn't cover:

  • Whether emulators were painting. The test machine may not have had an active display and the app panel wasn't necessarily open, so rendering may have been skipped. Their read loops were real, but capacities on a visible, painting terminal may be lower.
  • Real slow links, SSH sessions and tmux. Slow readers and stalls were produced by the scripted reader.
  • Full Metro builds on Windows, the Windows Terminal app and QuickEdit selection pauses.
  • Real warnings. The main-thread lines are synthetic, and one per module is deliberately heavy. Linux wasn't measured, and this is one app on one machine.
PTY reader with a set read speed
#!/usr/bin/env python3
"""Runs a command on a real PTY and drains the master side at a bounded rate.

--rate 0 reads as fast as possible. --stall-at/--stall-for stop reading for a window.
--xoff-at/--xoff-for send ^S and ^Q through the line discipline instead."""
import argparse, fcntl, os, pty, select, signal, struct, sys, termios, time

p = argparse.ArgumentParser()
p.add_argument('--rate', type=float, default=0)
p.add_argument('--stall-at', type=float, default=-1)
p.add_argument('--stall-for', type=float, default=0)
p.add_argument('--xoff-at', type=float, default=-1)
p.add_argument('--xoff-for', type=float, default=0)
p.add_argument('--cols', type=int, default=120)
p.add_argument('--rows', type=int, default=40)
p.add_argument('--save', default=None)
p.add_argument('--max-seconds', type=float, default=240)
p.add_argument('cmd', nargs=argparse.REMAINDER)
a = p.parse_args()
cmd = a.cmd[1:] if a.cmd and a.cmd[0] == '--' else a.cmd

pid, fd = pty.fork()
if pid == 0:
    os.execvp(cmd[0], cmd)
fcntl.ioctl(fd, termios.TIOCSWINSZ, struct.pack('HHHH', a.rows, a.cols, 0, 0))
os.kill(pid, signal.SIGWINCH)

save = open(a.save, 'wb') if a.save else None
t0 = time.monotonic()
total = 0
xoffed = xoned = False
chunk = 65536 if a.rate == 0 else max(1, min(4096, int(a.rate / 100) or 1))
while True:
    now = time.monotonic() - t0
    if now > a.max_seconds:
        os.killpg(pid, signal.SIGKILL)
        print('WATCHDOG killed', file=sys.stderr)
        break
    if a.xoff_at >= 0 and not xoffed and now >= a.xoff_at:
        os.write(fd, b'\x13'); xoffed = True
    if xoffed and not xoned and now >= a.xoff_at + a.xoff_for:
        os.write(fd, b'\x11'); xoned = True
    if a.stall_at >= 0 and a.stall_at <= now < a.stall_at + a.stall_for:
        time.sleep(0.01); 
        continue
    if a.rate > 0:
        allowed = a.rate * now - total
        if allowed < 1:
            time.sleep(min(0.01, (1 - allowed) / a.rate))
            continue
    r, _, _ = select.select([fd], [], [], 0.05)
    if fd in r:
        try:
            data = os.read(fd, chunk if a.rate == 0 else max(1, min(chunk, int(allowed))))
        except OSError:
            break
        if not data:
            break
        total += len(data)
        if save: save.write(data)
    else:
        done, _ = os.waitpid(pid, os.WNOHANG)
        if done:
            pid = 0
            break
if pid:
    try: os.waitpid(pid, 0)
    except OSError: pass
print(f'pty drained {total} bytes in {time.monotonic()-t0:.2f}s', file=sys.stderr)
PTY buffer measurement
# Measures how many bytes a PTY (or pipe) accepts with nobody reading before a write blocks.
import os, pty, fcntl, termios, select, time
def cap(w, n):
    fl = fcntl.fcntl(w, fcntl.F_GETFL); fcntl.fcntl(w, fcntl.F_SETFL, fl | os.O_NONBLOCK)
    t = 0; b = b'x' * n
    while True:
        try:
            t += os.write(w, b)
        except BlockingIOError:
            return t
for n in (100, 1024):
    m, s = pty.openpty()
    print('pty chunk', n, 'capacity', cap(s, n)); os.close(m); os.close(s)
r, w = os.pipe(); print('pipe capacity', cap(w, 1024))
