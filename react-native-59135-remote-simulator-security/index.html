Running pull requests on remote iOS simulators

Whether a maintainer comment is enough to protect the credentials and machines behind Argent Cloud iOS E2E runs, checked against the PR's workflows and tested against Maestro, the iOS Simulator and the published sim-remote client, with a proposed alternative.

react/react-native#59135 by Juliusz Wajgelt (@jwajgelt) moves iOS Maestro E2E from macos-26-large runners to ubuntu-latest driving Argent Cloud remote simulators, with run times of about 35 minutes against 71–102 minutes. That speedup is worth having. Fork PRs get no OIDC token, so the PR moves their runs behind a maintainer comment, @react-native-bot e2e-tests. Nicola Corti (@cortinico) asked whether an agentic review could suggest that command.

The better fix is architectural: keep PR code out of any job that can mint a token, treat the fleet host as the place hostile code runs, and then run automatically. Neither a trusted build artefact nor AI review can replace that. Both can help once a bad decision can only waste machine time.

What's at risk

The risks below are ranked by what a malicious PR can reach. None of them is live: the PR hasn't landed, and nothing here was tried against Argent's fleet.

Token theft
The on-demand Debug template app job runs PR code with id-token: writeinit-project-e2e.js installs the PR's react-native-package, then maestro-ios runs yarn start from it. PR code can request tokens for any audience, identified as e2e-ios-on-demand.yml on main. That gives it the Argent login, and anything else that trusts that workflow. Fix: Run Release only on this path until Metro runs outside the token's job.
Unknown
Nothing establishes what a PR-built .app can do to the fleet hostThe PR-built app is native code on Argent's Mac, and the Simulator isn't a virtual machine. Argent's README doesn't describe isolation between leases. Text in the published client says release erases the simulators, which doesn't describe the host, and spawn can upload a binary and leave it running. Isolation may well exist, so this is a question for Argent. It decides whether fork PRs can run at all.
Supply chain
Third-party code floats in the token's jobargent-cloud-actions/*@v2 is a moving tag, and install always fetches the latest sim-remote, with no version input or checksum. A compromise of either repository reaches every run's token. Fix: Pin actions to SHAs, as the repository's other trusted workflows do, and restore a version and checksum in install.
File read
PR-supplied flows can read runner files and send them anywhereSee the test results below. The direct route to the OIDC request token failed, but only because of an HTTP client length check. Fix: Run flows outside the token's job.
Coverage loss
Fork PRs lose automatic iOS E2E, and the hint meant to replace it doesn't reach themFork PRs were 704 of 789 Test All PR runs. e2e-ios-suggest.yml finds the PR through commits/<sha>/pulls, which returned an empty list for a fork's head on react/react-native#59551, so its hint is skipped there.

Why a trusted artefact doesn't solve this

A clean build gives provenance, not safety. An attestation can prove which commit and recipe produced the bytes, but a PR's .app is still the PR's native code, however faithfully it was built. The build also executes PR-controlled scripts, such as podspecs, Gradle files and codegen.

Meaningful provenance also has a cost. A pull_request run uses the PR's own workflow files, so the builder has to be defined from the base branch, through pull_request_target or workflow_run. Those run in the default branch's cache scope, where PR code running in the job can poison caches that later main runs restore. pull_request builds have no OIDC token, a read-only token and an isolated cache.

The artefact isn't the gap. Keep builds on pull_request, treat their output as hostile, and control where it runs. Attestation can come later for attribution: if a malicious run happens, it shows which commit produced it.

Why AI review can't be the gate

An AI reviewer reads attacker-controlled text, so prompt injection is part of its threat model. It also can't evaluate a compiled binary, or what a build script does at run time. A false negative hands over the token. The repository's own AI review workflow makes the same point about its /review command: "gate controls who triggers, not what code runs".

It's still useful for scheduling. It can suggest which PRs deserve a run and flag sensitive paths for a human. Reviewing fork PRs needs a model key in a base-context job, so that job needs no tools, and its output should be an allowlisted value. The existing should_test_ios path filter is deterministic and already skips iOS on 167 of the PR runs measured, so it's the first thing to try, with AI added only if that proves too blunt.

A model that doesn't depend on review

The job is the boundary, not the step. ACTIONS_ID_TOKEN_REQUEST_* is in the environment of every step, and later steps in a job share a user with passwordless sudo on GitHub-hosted runners. So PR code and the token have to live in different places.

ZoneTriggerHoldsRuns
Build (hostile)pull_requestNothingBuilds the app and JS bundle, collects flows, as it does today
Broker (trusted)workflow_run from mainOIDC tokenmain code and pinned actions, with PR output handled as data
Execute (hostile)Started by the brokerOne leaseApp, Maestro, flows, Metro, with damage bounded by the lease

Option A: hosted test run (recommended)

The broker uploads the app and flows, and Maestro runs on the leased machine. The runner only polls and downloads results. The previous Maestro Cloud setup took this shape. It needs a submit-and-poll API from Argent, and the client's sim-remote build looks like a similar shape. Start with Release, since Debug also needs Metro on the fleet.

Option B: container on the runner

The broker acquires a machine on the host, then runs Maestro, flows and Metro in a locked-down container with only the client's daemon socket mounted. That needs no Argent changes and keeps the token, runner files and sudo out of reach. It's a design only: whether the socket and Maestro shims work across the boundary is untested.

Both options need the same things from Argent: a host reimage or virtual machine per lease, or at the very least per tenant, with no shared credentials on hosts. They also need leases limited to one machine with a short lifetime, plus an OIDC audience bound to Argent's router, which couldn't be determined from the client.

Recommendation

  • Don't land the on-demand Debug path. Run Release only on PRs until Metro runs outside the token's job.
  • Pin the Argent actions and client, and narrow id-token: write to the one job that needs it.
  • Ask Argent about host isolation first. The answer decides whether fork PR binaries can run there at all.
  • Build the broker and execute split, with a hosted test run as the target and the container as the fallback.
  • Then run automatically on PRs where Test All ran, with budgets. Add AI only as a scheduling hint, if the path filter proves too blunt.

Method

The workflow findings come from reading the PR at ebff67b. Nothing from the PR was executed. The fork lookup was checked with one API call on react/react-native#59551. Volumes come from the Actions API for Test All runs from 2026-10-22 16:28 UTC to 2026-10-29 15:45 UTC, counting 789 PR runs on 299 distinct head branches, 704 of them from forks. Branch names are an approximation of PRs. The 167 path-filtered runs come from the same data across pre-pause PR runs.

Statements about Argent come from its public actions repository and README, and from text in the published sim-remote 1.0.0 macOS binary, read with strings and not executed. That makes them weaker evidence than the rest. Argent's servers and hosts weren't contacted or tested. Maestro's file read is a documented form of its HTTP API, not a bypass.

Not verified: file paths on a real GitHub-hosted runner, host access from inside an installed app, and either option in the proposed model.
